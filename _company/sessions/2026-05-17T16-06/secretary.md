# 🚨 시스템 장애 종합 보고서: LLM 호출 실패 패턴 분석

사장님, 지난 자율 사이클 동안 다수의 에이전트(Researcher, Writer 등)에서 반복되는 공통적인 기술적 오류가 발생했습니다. 이 문제는 단순한 '버그'라기보다는 **시스템 리소스 관리 및 아키텍처의 안정성** 문제로 보입니다.

## 🔍 1. 주요 장애 패턴 요약 (The "What")
*   **[반복 원인 A] Context Length 초과 위험:** 전문적이고 위기감을 강조하는 콘텐츠 기획(SYSTEM OVERLOAD 콘셉트)은 과학적 데이터를 많이 활용하게 만듭니다. 이로 인해 Context Window가 급격히 증가하여 LLM의 처리 한계에 도달하고 있습니다. [근거: 영숙 개인 메모리, 지난 의사결정 로그]
*   **[반복 원인 B] 리소스 부족 및 Timeout:** 복잡한 다중 에이전트 프로세싱(Writer → Designer → Leo 등) 과정에서 LLM API 호출 실패가 빈번합니다. 특히 '모델 로드 대기 240초 초과'와 같은 **타임아웃 오류**가 명확히 관찰됩니다. [근거: 코다리 에이전트 산출물, 지난 의사결정 로그]
*   **[반복 원인 C] 모델 크기 및 메모리 비효율:** 시스템은 대형 모델을 사용하려 시도하지만, 실제 환경에서는 메모리 부족(Memory Limitation) 문제가 발생하여 더 작은 안정적인 모델로의 전환이 지속적으로 요구되고 있습니다. [근거: 지난 의사결정 로그, 영숙 개인 메모리]

## ⚙️ 2. Developer를 위한 우선순위 해결 리스트 (Action Items)
아래 순서대로 개발팀에 전달해 주시면 가장 효율적입니다. **가장 시급한 것은 안정화(Stabilization)**입니다.

### 🥇 [최우선/P1] 시스템 자원 관리 및 재시도 로직 구축 (Critical Blocker)
*   **목표:** LLM 호출 실패로 인한 전체 워크플로우 중단을 막고, 자동 복구 메커니즘을 만듭니다.
*   **세부 액션:**
    1.  **모델 스케일링 자동화:** 현재 컨텍스트 길이와 메모리 용량을 실시간으로 체크하여, 대형 모델 호출 시도가 실패하면 자동으로 **가장 작고 안정적인 대체 모델(예: gemma2:2b 등)**로 전환하는 로직을 구현합니다. [근거: 코다리 에이전트 산출물]
    2.  **타임아웃 재설정:** LLM API 통신 불안정성을 해결하기 위해, 시스템 timeout 값을 기존보다 늘려(예: 600초) 충분한 처리 시간을 확보해야 합니다. [근거: 지난 의사결정 로그]
*   **테스트 케이스:** Context Length가 임계치를 넘는 더미 데이터를 주입하여 시스템이 자동으로 작은 모델로 다운그레이드되는지 테스트합니다.

### 🥈 [차순위/P2] 데이터 핸들링 및 아키텍처 개선 (Mid-Term Goal)
*   **목표:** 콘텐츠의 전문성을 유지하면서도 Context Overload를 방지하는 구조적 방법을 마련합니다.
*   **세부 액션:**
    1.  **정보 분할(Chunking):** 대량의 과학적 데이터나 장문의 리서치 결과는 LLM에 한 번에 넣지 않고, **'진단 과정 → 증거 제시 → 해결책 제안'**의 단계별로 잘게 쪼개어 (Chunk) 순차적으로 입력합니다. [근거: 영숙 개인 메모리]
    2.  **API 권한 재검증 루틴:** API 데이터 오류가 감지되면, 개발 로직 내에 **사용자/계정의 유효 기간 및 권한을 먼저 확인하는 체크(Pre-Check) 단계**를 필수적으로 삽입합니다. [근거: 지난 의사결정 로그]
